# Phase 1.5: Deploy preview - Research

**Researched:** 2026-04-21
**Domain:** SvelteKit 2 PWA deployment to Netlify (preview + production) + real-iOS-Safari UAT of three Phase 1 carry-overs
**Confidence:** HIGH for adapter-netlify v6 mechanics, netlify.toml syntax, preview URL scheme; MEDIUM for iOS 17/18 PWA install heuristics (device-specific variance); MEDIUM for vite-plugin-pwa × Netlify production caching edge cases (no direct 2026 reports, pattern generalises from 1P tools).

## Summary

Phase 1.5 is a **plumbing phase** — one-line `svelte.config.js` swap (`adapter-auto` → `adapter-netlify@^6.0.4`), a new `netlify.toml` at repo root (~30 lines: `[build]`, `[build.environment]`, five `[[headers]]` blocks for the Standard PWA profile), one-time manual GitHub OAuth link in the Netlify UI, then push a PR and use the auto-issued `deploy-preview-1--moodlog.netlify.app` URL for on-device UAT.

**Two non-obvious 2026 findings drive the plan:**

1. **adapter-netlify v6 (current latest 6.0.4, 2026-02-24) uses the modern Netlify Functions v2 API** [CITED: github.com/sveltejs/kit PR #15203, netlify/blog/migrating-breaking-changes]. Key win for us: the old "you cannot specify redirects in netlify.toml, must use _redirects" limitation is **lifted**. We therefore do **not** need a `_redirects` file. With zero `+page.server.ts` files today (Pitfall 7 guard), zero functions get generated, and the deploy is effectively a static deploy — free tier, no cold starts, no per-request cost.

2. **iOS 16.4+ web push works only inside an installed PWA** [CITED: developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers]. Our scheduler.ts uses `setInterval`, **not** Web Push / VAPID. Consequence: reminders fire only while the PWA tab/window is foreground. **iOS stops `setInterval` callbacks entirely when the app is backgrounded** [CITED: firt.dev/understanding-js-background/]. Phase 1's InstallBanner + OnboardingSheet step-1 copy already surfaces this honestly ("Install to Home Screen to enable reminders"). Phase 1.5 UAT for HUMAN-UAT #1 (real-device notification delivery) must therefore be run with the app **foreground for the full ~2 minutes** between setting reminder_time and the fire event — not as a background test. This matches the expectation recorded in `01-VERIFICATION.md` `human_verification[0].why_human` and is not a new constraint; the research just makes it test-procedure-explicit.

**Primary recommendation:** Ship a minimal `netlify.toml` (build + Node 22 + 5 headers blocks, no redirects, no build plugins), swap the adapter default-options, commit on a feature branch, do the GitHub→Netlify OAuth link in the UI, and run the three UAT items on the first auto-issued preview URL with the app kept foreground during the notification window.

### Locked Decisions

**Git trigger strategy**

- **D-03:** Phase 1.5 itself will be the first PR. Development of Phase 1.5 happens on a feature branch pushed to origin, producing the first PR-preview URL. That URL is used to run the three HUMAN-UAT items before the PR merges.

**Build output shape**
- **D-04:** Use the default `@sveltejs/adapter-netlify` behavior (serverless-capable, prerenders what it can, generates functions for any `+page.server.ts`). Do NOT force prerender-all.
- **D-05:** Phase 2 will decide whether auth runs client-side (stay effectively static) or via a serverless function — Phase 1.5 must not preempt that choice.
- **D-06:** Today there are zero `+page.server.ts` files (Pitfall 7 guard) so the deployed output is fully static in practice. No functions are invoked per request, cost stays at the free tier.

**Cache + security headers (netlify.toml [[headers]])**
- **D-07:** Service worker must never be cached by the CDN — `/service-worker.js` gets `Cache-Control: no-cache` (or `public, max-age=0, must-revalidate`). This avoids the "stale SW installed forever" class of bugs.
- **D-08:** SvelteKit's `_app/immutable/*` bundle (content-hashed) gets `Cache-Control: public, max-age=31536000, immutable`.
- **D-09:** `/manifest.webmanifest` gets `Cache-Control: public, max-age=3600` (short, since manifest changes may need to propagate quickly).
- **D-10:** Manifest icons (`/manifest-icon-192.png`, `/manifest-icon-512.png`, `/apple-touch-icon.png`) get `Cache-Control: public, max-age=31536000` — when icons change we bump their filenames.
- **D-11:** CSP stays in `src/app.html` meta tag as the single source of truth. Do NOT mirror it as an HTTP header in netlify.toml — two copies drift; one copy is easier to maintain. Revisit if meta-based CSP proves insufficient against a specific attack vector (none anticipated for a local-only app).
- **D-12:** Skip `Service-Worker-Allowed` header. Our SW is at root (`/service-worker.js`) and controls `/` by default — no scope extension needed.

**Netlify site identity**
- **D-13:** Site lives under the user's personal Netlify account, not a JobRad org account. Ownership portable across employment.
- **D-14:** Requested slug: `moodlog.netlify.app`. Fallbacks if taken: `moodlog-app.netlify.app`, `holgergp-moodlog.netlify.app`, or Netlify auto-generated. Plan should document the chosen final slug at execution time.

## Architectural Responsibility Map

Phase 1.5 adds a deployment tier and a CDN tier. No new client-side or server-side logic is introduced.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Build pipeline | Netlify build container (Linux) | Local developer machine | `npm run build` runs identically in both; Node version pinned. |
| Static asset serve | Netlify CDN | — | `_app/immutable/*`, `/manifest.webmanifest`, icons, root HTML. |
| HTTP header injection | Netlify CDN (`[[headers]]` rules) | — | Cache-Control + any future security headers. CSP stays in-HTML (D-11). |
| SPA routing / 404 fallback | adapter-netlify v6 generated routing | — | Emitted in Function manifest; no `_redirects` file needed [CITED]. |
| HTTPS / TLS | Netlify automatic Let's Encrypt (wildcard on `*.netlify.app`) | — | Auto-issued for production site, deploy previews, branch deploys [CITED: answers.netlify.com wildcard SSL thread]. No action needed. |
| Git → deploy trigger | GitHub webhook → Netlify build | — | Installed once via OAuth link in Netlify UI (D-15). |
| Service worker serve | Netlify CDN | — | Served from `build/service-worker.js` with `Cache-Control: no-cache` per D-07. |
| PWA install + storage persist | iOS Safari / Chrome Android | — | Browser-only; Phase 1 code unchanged. Deployment just provides the HTTPS host. |
| Notification fire (setInterval) | Browser (foreground only on iOS) | — | Pitfall 2 from Phase 1 RESEARCH confirmed again below. |

**Tier misassignment to watch for:**
- A plan that adds a `_redirects` file is a tier error — v6 adapter owns that surface.
- A plan that duplicates CSP into a netlify.toml header is a D-11 violation.
- A plan that proposes Edge Functions or `split: true` to "make it fast" preempts D-04/D-05 decisions — refuse. Default serverless shape is locked.

### Pattern 1: Adapter Swap (minimal diff)
**What:** One-line change in svelte.config.js. Default options; no `edge`, no `split`.
**When to use:** Exactly once, in the Phase 1.5 task.
**Example:**
```javascript
// svelte.config.js  (AFTER — diff shown inline)
- import adapter from '@sveltejs/adapter-auto';
+ import adapter from '@sveltejs/adapter-netlify';

  /** @type {import('@sveltejs/kit').Config} */
  const config = {
    compilerOptions: {
      runes: ({ filename }) => (filename.split(/[/\\]/).includes('node_modules') ? undefined : true)
    },
    kit: {
-     adapter: adapter()
+     adapter: adapter()  // default: serverless functions on demand, static where possible
    }
  };

```
Source: [CITED: svelte.dev/docs/kit/adapter-netlify] — "Add it to `svelte.config.js`: `import adapter from '@sveltejs/adapter-netlify'; export default { kit: { adapter: adapter() } };`"

### Pattern 2: netlify.toml for a Static-in-Practice SvelteKit PWA
**What:** A single netlify.toml at repo root carrying build info + the five Cache-Control header blocks specified by D-07..D-10.
**When to use:** Exactly once, in Phase 1.5.
**Example (Code Example 1 — the full file):**
```toml
# netlify.toml — MoodLog deploy contract
# Header decisions locked in Phase 1.5 CONTEXT.md (D-07..D-12).
# CSP stays in src/app.html meta tag (D-11) — do NOT mirror here.

[build]
  command = "npm run build"
  publish = "build"

[build.environment]
  NODE_VERSION = "22"

# Service worker must never be CDN-cached (D-07) — update propagation
# is the whole point of the browser-side SW registration lifecycle.
[[headers]]
  for = "/service-worker.js"
  [headers.values]
    Cache-Control = "public, max-age=0, must-revalidate"

# Content-hashed SvelteKit bundles — immutable, cache for a year (D-08).
[[headers]]
  for = "/_app/immutable/*"
  [headers.values]
    Cache-Control = "public, max-age=31536000, immutable"

# Web manifest — short cache so manifest edits propagate within an hour (D-09).
[[headers]]
  for = "/manifest.webmanifest"
  [headers.values]
    Cache-Control = "public, max-age=3600"

# Manifest icons — static asset names, change = rename = cache-bust (D-10).
[[headers]]
  for = "/manifest-icon-192.png"
  [headers.values]
    Cache-Control = "public, max-age=31536000"

[[headers]]
  for = "/manifest-icon-512.png"
  [headers.values]
    Cache-Control = "public, max-age=31536000"

[[headers]]
  for = "/apple-touch-icon.png"
  [headers.values]
    Cache-Control = "public, max-age=31536000"
```
Sources: [CITED: docs.netlify.com/routing/headers/] syntax; [CITED: svelte.dev/docs/kit/adapter-netlify] minimal `[build]` contract; [CITED: docs.netlify.com/build/configure-builds/manage-dependencies] Node version pinning.

**Notes on the TOML above:**
- No `[[redirects]]` block. adapter-netlify v6 emits routing directly in the Function manifest [CITED: github.com/sveltejs/kit PR #15203]. With zero `+page.server.ts` files, no function is generated, and the static output + SvelteKit's client-router handles SPA fallback.
- `publish = "build"` is the adapter-netlify default; specifying it explicitly makes the deploy contract visible to anyone reading netlify.toml without cross-referencing adapter docs.
- `NODE_VERSION = "22"` uses the latest LTS (Node 22 went LTS in Oct 2024). SvelteKit 2.57 and adapter-netlify 6.0.4 are both Node-22-clean.
- Header name case is case-insensitive per TOML + HTTP spec [CITED: docs.netlify.com/routing/headers/] — `Cache-Control` used here for readability.

### Pattern 3: First-Time GitHub → Netlify OAuth Link
**What:** One-time, web-UI-only step. Cannot be automated. Must be flagged as a human-action checkpoint in the plan.
**When to use:** Exactly once, in Phase 1.5, before the first PR push.
**Flow (source: [CITED: docs.netlify.com/frameworks/sveltekit/] and standard Netlify onboarding):**
1. Log in at `app.netlify.com` under the user's **personal** account (D-13).
2. "Add new site" → "Import an existing project" → "Deploy with GitHub".
3. Authorize the Netlify GitHub App for `holgergp` — grant access to the `moodlog` repo only (least-privilege; avoid org-wide).
4. Pick `moodlog` repo. Netlify auto-detects SvelteKit and suggests: build `npm run build`, publish `build`, dev `vite dev` [CITED: docs.netlify.com/frameworks/sveltekit].
5. Accept defaults (netlify.toml will override/confirm these on first build anyway).
6. Change site name slug to `moodlog` (final URL: `moodlog.netlify.app`). If taken, fall back to `moodlog-app`, then `holgergp-moodlog`, then Netlify auto-gen. Document the chosen slug in SUMMARY.
7. Deploy — Netlify kicks a first build from `main` immediately. This is a **sanity-check deploy from the current main branch**, which does NOT yet have netlify.toml or the adapter swap. This first build will fail (adapter-auto hits non-Vercel-non-Netlify fallback) OR succeed with adapter-auto's Netlify detection — either way, not useful. The real Phase 1.5 preview comes from the PR push in step 8.
8. Push the Phase 1.5 feature branch to origin. Open the PR. Netlify auto-issues `deploy-preview-1--moodlog.netlify.app`. Run UAT on that URL.

**Auto-deploy behavior (defaults on a fresh site):** PR previews enabled automatically for all PRs against the production branch (main) [CITED: docs.netlify.com/site-deploys/deploy-previews/]. No config needed.

### Anti-Patterns to Avoid
- **Adding `_redirects` file.** adapter-netlify v6 owns routing now [CITED]. A manual `_redirects` will not be read by functions (routing is in code) and may conflict with the SvelteKit router. Don't.
- **Duplicating CSP into a netlify.toml header.** D-11 — single source of truth. Two copies will drift within one maintenance cycle.
- **Setting `registerType: 'prompt'`.** vite-plugin-pwa is configured `autoUpdate` in `vite.config.ts` — do not touch. Changing it is out of scope and would interact with D-07's no-cache SW.
- **Adding a build plugin in netlify.toml.** Netlify's Lighthouse / a11y / similar plugins are tempting but out of scope (Lighthouse CI explicitly deferred per ROADMAP Phase 1.5 Notes).
- **Forcing prerender=true globally.** Preempts D-04/D-05. The existing `+page.ts` files' `ssr=false` flags stay; no global prerender override.
- **Adding env vars to netlify.toml.** None are needed for runtime today. Phase 2 may add auth secrets — that's Phase 2's contract to set via the Netlify UI (never committed to git).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SPA fallback / 404 routing | Custom `_redirects` with `/*  /index.html  200` | adapter-netlify v6 emits routing in Function manifest | Adapter owns this; manual redirects fight the router on prerendered routes. |
| HTTPS certificate management | Any manual cert config | Netlify auto-Let's-Encrypt on `*.netlify.app` | Free, automatic, covers all preview/branch subdomains via wildcard [CITED]. |
| Deploy hooks / Git triggers | Webhook scripts, GitHub Actions deploy | Netlify's built-in GitHub App | One-click, no secrets to manage. |
| Build caching | Custom ci caching config | Netlify's default npm cache | Zero-config; respects package-lock.json. |
| Node version in CI | Conditional `nvm` scripts | `NODE_VERSION = "22"` in `[build.environment]` | Netlify reads this natively. |
| Notification scheduling on iOS | VAPID push server, background workers | **Accept the limitation**; foreground-only reminders + install nudge | Phase 1 scope locked; v2 backlog. |

**Key insight:** Phase 1.5 is almost entirely "stop touching things that Netlify already does." The adapter emits routing, the CDN emits HTTPS, the GitHub App emits webhooks, the build cache is automatic. The only hand-written surface is the five `[[headers]]` blocks — because Cache-Control semantics are *our* decision, not the platform's.

## Common Pitfalls

### Pitfall 1: First Netlify build happens on `main` **before** netlify.toml exists
**What goes wrong:** Step 7 of Pattern 3 above — when the GitHub repo is linked, Netlify kicks an immediate build from the current `main` tip. `main` at Phase 1.5 start has `adapter-auto` and no netlify.toml, so the first build either fails or produces a weird half-configured deploy at `moodlog.netlify.app`.
**Why it happens:** Netlify's default onboarding auto-deploys main as a "show you it works" gesture.
**How to avoid:** Treat the first main-deploy as **throwaway**. The real Phase 1.5 validation happens on the PR preview URL. Document this in the task summary so the user doesn't chase a phantom bug on the production URL until the PR merges.
**Warning signs:** Production URL (`moodlog.netlify.app`) returns 404 or shows wrong content — this is expected until PR merges; UAT is on `deploy-preview-1--moodlog.netlify.app`.
**Source:** Direct inference from [CITED: docs.netlify.com/frameworks/sveltekit/] onboarding flow + standard Netlify behavior.

### Pitfall 2: iOS `setInterval` stops firing when the app backgrounds
**What goes wrong:** HUMAN-UAT #1 (notification delivery) tests if the evening reminder fires at the configured time. Phase 1's scheduler is `setInterval` ticking every 60s. On iOS Safari (installed PWA or not), `setInterval` callbacks are paused/throttled heavily when the tab or PWA is backgrounded [CITED: firt.dev/understanding-js-background/]. If the user installs the PWA, sets `reminder_time = 21:00`, then puts the phone down — the scheduler never ticks, the notification never fires.
**Why it happens:** iOS enforces aggressive background JS suspension to save battery. WebKit bug 211018 documents this for service workers specifically [CITED: bugs.webkit.org/show_bug.cgi?id=211018]. Only **Web Push with VAPID** can deliver notifications when the app is backgrounded on iOS, and Phase 1 explicitly scoped out VAPID (Phase 2+ additive feature per Phase 01-05 SUMMARY key-decisions).
**How to avoid in Phase 1.5 UAT:** Set `reminder_time` ~2 minutes in the future **and keep the app foreground for the full 2 minutes**. This is the test that HUMAN-UAT #1 actually needs — it verifies the scheduler + SW deep-link, **not** backgrounded delivery. Plan 01-VERIFICATION.md `human_verification[0].why_human` already anticipates this; the test procedure in Phase 1.5's plan must make it explicit.
**Warning signs:** User tests with app backgrounded → notification never fires → user assumes the feature is broken. (It's not; it's out-of-scope until Phase 2+ VAPID.)
**Source:** [CITED: firt.dev/understanding-js-background/] "On iOS setTimeout and setInterval won't work once your app is in background."

### Pitfall 3: iOS web push requires installed PWA **and** user gesture for permission
**What goes wrong:** HUMAN-UAT #1 procedure says "grant notification permission during onboarding step 2". If the user tests from a non-installed Safari tab, `Notification.requestPermission()` throws/returns unavailable on iOS.
**Why it happens:** iOS 16.4+ gated web push to installed PWAs only [CITED: developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers]. Plus: on iOS, permission prompts require a direct user gesture — programmatic grant (even in response to an async chain after a gesture) can be rejected.
**How to avoid:** UAT script must go: visit URL → Share → Add to Home Screen → open from Home Screen (standalone mode) → **then** run onboarding → **then** grant permission. If testing from a Safari tab, the permission path won't work and that is expected.
**Warning signs:** Onboarding step 2 "Allow notifications" button does nothing or throws when clicked from a non-installed Safari tab.
**Source:** [CITED: academy.insiderone.com/docs/web-push-support-for-mobile-safari]; [CITED: developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers].

### Pitfall 4: EU iOS users may have PWA support disabled (DMA aftermath)
**What goes wrong:** Per CLAUDE.md the user is at `@jobrad.org` (German company). If the user tests on a phone locale-set to an EU region on iOS 17.4, PWA install may behave unexpectedly.
**Why it happens:** Apple initially removed EU PWA support in iOS 17.4, then **reversed the decision** [CITED: dev.to/lilxyzz/ios-174-update-ends-pwa-support-in-the-european-union-3p95, brainhub.eu/library/pwa-on-ios]. In 2026, EU PWA support is restored to the same constraints as rest-of-world. Net effect: no current restriction.
**How to avoid:** Nothing to change in code or config. Documented here so if the UAT shows weird behavior ("Share sheet doesn't offer Add to Home Screen"), the user knows this is not a regression introduced by Phase 1.5 — it would be a device-specific iOS bug worth filing with Apple, not our problem to fix.
**Warning signs:** iOS Safari Share sheet missing "Add to Home Screen" option.
**Source:** [CITED: brainhub.eu/library/pwa-on-ios] — "in terms of what you can actually build with a PWA on an iPhone today, nothing has materially changed" (post-reversal).

### Pitfall 5: Service-worker scope on deploy-preview URL vs production URL
**What goes wrong:** The service worker registered on `deploy-preview-1--moodlog.netlify.app` has scope `/` for that exact origin. When the user later visits `moodlog.netlify.app` (production), it's a **different origin**, and the SW registers fresh. If the user tests on preview then tries to install on production, IndexedDB entries do NOT transfer (origin-scoped).
**Why it happens:** Every `*.netlify.app` subdomain is a separate origin by browser security model.
**How to avoid:** Run HUMAN-UAT items on **one** URL (the PR preview) and treat it as the authoritative test. After PR merges, production URL is a fresh install — don't expect preview-URL entries to appear there. For 7-day eviction survival (HUMAN-UAT #3), decide at UAT time whether to run it on preview or wait for production. Recommendation: run on production (post-merge) because: (a) the slug is more stable, (b) preview URLs can be deleted when the PR closes.
**Warning signs:** User runs UAT #2 on preview, merges PR, visits production URL, entries are gone. Not a bug — different origin.
**Source:** Standard browser origin semantics; [CITED: docs.netlify.com/site-deploys/deploy-previews] confirms each preview is a distinct hostname.

### Pitfall 6: vite-plugin-pwa `injectManifest` compile step on Netlify's build container
**What goes wrong:** Plan 05 hit a Workbox `__WB_MANIFEST` tree-shaking bug locally, fixed via side-effectful assignment in `src/service-worker.ts:29-30`. The fix is source-level, so it survives into Netlify's build. But: Netlify's build container uses a different Node + esbuild + Vite combo — the specific tree-shake behavior that prompted the fix could theoretically behave differently.
**Why it happens:** vite-plugin-pwa injectManifest strategy compiles the SW at build time; workbox-build does a string find-and-replace on `self.__WB_MANIFEST`. Any build environment where Vite's tree-shaker behaves differently could revert the bug.
**How to avoid:** The existing fix (side-effectful assignment to `__moodlog_precache_manifest`) is robust across Vite versions because it's a real statement with real semantic side effect — not a tree-shake dance. **Verification step in Phase 1.5 plan:** after first successful Netlify build, download or view the compiled `/service-worker.js` (via curl from the preview URL) and grep for the precache manifest array — if the array has 22+ entries (matching local build), the injection survived the production build.
**Warning signs:** Preview URL loads, but DevTools → Application → Service Worker shows "no precache" or an empty manifest. Lighthouse PWA audit fails with "no offline support".
**Source:** Inference from Phase 01-05 SUMMARY deviation Rule 3 + general build-tooling reasoning. [CITED: github.com/vite-pwa/sveltekit].

### Pitfall 7: Header `for = "/manifest.webmanifest"` spelling
**What goes wrong:** vite-plugin-pwa emits the manifest at `/manifest.webmanifest` (note: `.webmanifest` with no hyphen, not `/manifest.json`). A typo in netlify.toml (`/manifest.json` or `/web.manifest`) means the header never applies and the manifest gets Netlify's default Cache-Control.
**Why it happens:** Multiple valid manifest extensions exist in the wild; vite-plugin-pwa uses `.webmanifest` specifically.
**How to avoid:** Copy-paste the path from `vite.config.ts` / actual build output. Smoke-test post-deploy with:
```bash
curl -I https://deploy-preview-1--moodlog.netlify.app/manifest.webmanifest
# Expect: Cache-Control: public, max-age=3600
```
**Warning signs:** `curl -I` shows `Cache-Control: max-age=0, must-revalidate` (Netlify default for HTML-like content) instead of the 3600 we specified.
**Source:** Direct inference; [CITED: github.com/vite-pwa/sveltekit README] — manifest path `manifest.webmanifest`.

### Pitfall 8: `build/` directory conflicts between adapter output and Vite's own default
**What goes wrong:** SvelteKit's default output is `.svelte-kit/output/`. adapter-netlify repackages that into `build/`. Vite's default `dist/` is unused. If netlify.toml says `publish = "build"` but the adapter for some reason writes to `dist/`, the deploy ships empty.
**Why it happens:** Misreading the stack — SvelteKit adapters, not Vite, decide the final output path.
**How to avoid:** Trust the adapter default; keep `publish = "build"`. After first local `npm run build`, verify `ls build/` shows content (index.html, `_app/`, `manifest.webmanifest`, etc.).
**Warning signs:** Netlify build log says "deploy directory 'build' is empty" or similar.
**Source:** [CITED: svelte.dev/docs/kit/adapter-netlify] — "Default publish directory: 'build'".
